# AeroLink Recovery Runbook

Goal: bring the application (`transnova.online`) and ArgoCD (`argocd.transnova.online`) back up.

There are **three independent root causes** plus one half-finished terraform apply. Fix them in order.

---

## 0. Fix your kubeconfig / AWS CLI first (quick)

`aws eks update-kubeconfig --name aerolink-dev` failed because the cluster is **not** named `aerolink-dev`.
In `infrastructure/terraform/modules/eks/main.tf` the cluster is `${prefix}-eks`, i.e.:

```powershell
aws eks update-kubeconfig --name aerolink-dev-eks --region us-east-1
```

(Your existing `kubectl` context still works, which is why pods were visible.)

## 1. Backend pods CrashLoopBackOff — root cause: AWS credentials not injected (IRSA)

### Evidence
- All 7 services crash with:
  `CredentialsProviderError: Could not load credentials from any providers`
  (kafkajs → MSK IAM auth and the AWS SDK can't get credentials).
- `kubectl describe pod` shows the container env is only `NODE_ENV, PORT, AWS_REGION, KAFKA_AUTH, BAGGAGE_TABLE_NAME` — there is **no** `AWS_ROLE_ARN`, **no** `AWS_WEB_IDENTITY_TOKEN_FILE`, and **no** `aws-iam-token` projected volume.
- Those are injected by the EKS pod-identity webhook **only when the ServiceAccount carries the `eks.amazonaws.com/role-arn` annotation at the moment the pod is created**.
- The Helm chart already has the correct annotation
  (`services/baggage-service/helm/values.yaml`):
  `eks.amazonaws.com/role-arn: arn:aws:iam::432004895948:role/aerolink-dev-baggage-service-role`
  and this is the latest commit (`fix: attach IRSA role-arn to service ServiceAccounts`).

**Conclusion:** the annotation is in Git but was never applied to the live ServiceAccounts (ArgoCD is down, see §3), OR the pods are older than the annotation. The 150-min-old pods predate the fix.

### Verify
```powershell
# Does the live SA actually have the annotation?
kubectl get sa baggage-service -n aerolink -o yaml

# Does the IAM role even exist? (terraform errored — see §4)
aws iam get-role --role-name aerolink-dev-baggage-service-role
```

### Fix
**A. Make sure the IAM role exists.** If `get-role` returns NoSuchEntity, the IAM module wasn't applied — do §4 first.

**B. Make sure the SA has the annotation.** If it's missing, apply the chart (don't wait for ArgoCD):
```powershell
helm upgrade --install baggage-service services/baggage-service/helm -n aerolink
# repeat for the other 6 services, OR fix ArgoCD (§3) and let it sync
```
Or patch directly as a stopgap (do for each service SA):
```powershell
kubectl annotate sa baggage-service -n aerolink `
  eks.amazonaws.com/role-arn=arn:aws:iam::432004895948:role/aerolink-dev-baggage-service-role --overwrite
```

**C. Recreate the pods so the webhook injects the token** (annotation alone does nothing to running pods):
```powershell
kubectl rollout restart deploy -n aerolink `
  baggage-service booking-service checkin-service flight-service `
  identity-service notification-service payment-service
```

### Confirm fixed
```powershell
kubectl get pods -n aerolink           # should go Running 1/1
kubectl describe pod -n aerolink <baggage-pod> | findstr AWS_WEB_IDENTITY   # token now present
```
If pods still crash with the same credential error after this, the IAM OIDC provider isn't associated with the cluster — re-apply the EKS/IAM terraform (§4) which creates `aws_iam_openid_connect_provider`.

## 2. `transnova.online` — "Failed to contact the origin" (CloudFront)

### Root cause
That error is generated by **CloudFront when its origin is unreachable**. In
`infrastructure/terraform/modules/s3-cloudfront/main.tf` the origin is `var.alb_dns_name`.
In `environments/dev/main.tf` that value falls through to a **placeholder**:

```hcl
alb_dns_name = (
  var.alb_dns_name_override != "" ? var.alb_dns_name_override :
  module.eks_addons.alb_dns_name != "" ? module.eks_addons.alb_dns_name :  # output is hardcoded ""
  "dummy-alb.us-east-1.elb.amazonaws.com"                                   # <-- this is what's live
)
```

`module.eks_addons.alb_dns_name` is hardcoded to `""` in its `outputs.tf`, and `alb_dns_name_override` is unset → CloudFront is pointing at `dummy-alb...` which doesn't exist. (The apex `transnova.online` Route53 record → CloudFront is fine.)

### Fix
1. Get the **real** ALB DNS name created by the load-balancer controller for the webui ingress:
```powershell
kubectl get ingress -n aerolink -o jsonpath="{.items[*].status.loadBalancer.ingress[*].hostname}"
# or
aws elbv2 describe-load-balancers --query "LoadBalancers[].DNSName" --output table
```
2. Set it as the override and re-apply so CloudFront uses the real origin:
```powershell
cd infrastructure/terraform/environments/dev
terraform apply -var="alb_dns_name_override=k8s-aerolink-xxxx-xxxx.us-east-1.elb.amazonaws.com"
```
Note: the webui ALB only has healthy targets once the backend pods from §1 are Running, so do §1 first.

## 3. `argocd.transnova.online` — "site can't be reached" (no DNS record)

### Root cause
There is **no Route53 record for `argocd`** anywhere in the terraform. The only records created are
`api.transnova.online` (api-gateway module) and `transnova.online`/`www` (s3-cloudfront module), plus ACM
validation records. There is **no external-dns** deployment to auto-create it. The ArgoCD ALB ingress exists
(`modules/eks-addons/main.tf`), but nothing maps the hostname to it → DNS doesn't resolve.

### Fix
1. Find the ArgoCD ALB hostname:
```powershell
kubectl get ingress -n argocd argocd-server `
  -o jsonpath="{.status.loadBalancer.ingress[0].hostname}"
```
2. Create a Route53 **alias A record** `argocd.transnova.online` → that ALB. Quickest is the console
(Route53 → hosted zone transnova.online → create record, type A, alias to the ALB). Or add a terraform
resource in the route53/eks-addons module:
```hcl
resource "aws_route53_record" "argocd" {
  zone_id = var.zone_id
  name    = "argocd.${var.domain_name}"
  type    = "A"
  alias {
    name                   = data.aws_lb.argocd.dns_name   # data source on the ALB
    zone_id                = data.aws_lb.argocd.zone_id
    evaluate_target_health = false
  }
}
```
3. Get the initial admin password to log in:
```powershell
kubectl -n argocd get secret argocd-initial-admin-secret `
  -o jsonpath="{.data.password}" | %{ [Text.Encoding]::UTF8.GetString([Convert]::FromBase64String($_)) }
```

## 4. The half-finished terraform apply (errored.tfstate)

`infrastructure/terraform/environments/dev/errored.tfstate` exists (serial 100) and the root
`alb_dns_name` output is `""` — a previous `terraform apply` failed partway. This is likely why the IAM
roles / records in §1–§3 are missing or inconsistent.

```powershell
cd infrastructure/terraform/environments/dev
terraform plan      # see what's missing / drifted
terraform apply     # re-run to converge IAM roles, OIDC provider, records
```
Re-running apply (idempotent) should create any missing IAM roles and the OIDC provider needed for IRSA.
Investigate whatever resource originally errored before assuming a clean apply.
